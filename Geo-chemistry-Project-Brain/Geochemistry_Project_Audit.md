# سند بررسی وضعیت پروژه Geochemistry Analysis

**هدف سند:** این فایل برای واگذاری به یک ایجنت کدنویسی (AI Coding Agent) تهیه شده تا باگ‌های شناسایی‌شده را رفع و توسعه‌های پیشنهادی را پیاده‌سازی کند.

### یافته‌های مهم در حین اجرا

- **IDW تقریبی:** نسخه cKDTree با k=12 روی همان گرید به‌طور میانگین ۱۳٪ انحراف معیار داده با نسخه قدیمی (همه نقاط) دارد؛ با افزایش k کاهش می‌یابد. k در UI قابل تنظیم است.
- **ناسازگاری API تبدیل‌ها:** `_boxcox_transform` و `_yeojohnson_transform` کورتیو `(نتیجه, lambda)` برمی‌گردانند ولی بقیه فقط آرایه — در تست‌ها unwrap شد؛ اگر بخواهید یکدست می‌شود.
- **روش فرکتالی چندکلاسه:** اگر شکستگی Log-Log برای همه درصدها یکسان باشد، آستانه‌ها برابر و همه آنومالی‌ها در بالاترین کلاس قرار می‌گیرند (رفتار ذاتی موجود از قبل).
- **جدول ضریب G:** مقادیر جدول `G_COEFFICIENTS` از نوع int هستند (بدون `.0`) — آرایه‌شناسی صرفاً عددی است و خللی ندارد.
- **کریجینگ:** گرید پیش‌فرض ۶۰×۶۰ (به‌جای ۱۰۰×۱۰۰ IDW) چون الگوریتم سنگین‌تر است؛ اما در تست‌ها حتی با ۵۰۰ نقطه زیر ۱ ثانیه اجرا شد. نقاطی که نزدیک‌ترین داده‌شان بیش از یک‌سوم گستره نقشه است با NaN ماسک می‌شوند تا کریجینگ در بیابانِ بدون داده مقدار جعل نکند. `UniversalKriging` پارامتر `coordinates_type` نمی‌پذیرد (محدودیت pykrige) و جداگانه handle شد. پارامتر صحیح `nlags` است نه `n_lags` (خطای ابتدای کار).
- **ادغام Duplicate QC:** فرمت فایل قدیمی (شیت‌های Duplicate Samples + Duplicate_Data با Sample_ID/Duplicated_Sample_ID) حفظ شد. تفاوت‌ها با نسخه قدیمی: multiprocessing حذف شد (سرعت کافی است و در ویندوز مشکل‌ساز بود)، نمودار Thompson-Howarth خطی (غیرلگ) که کامنت‌شده بود حذف شد و نسخه Log نگه داشته شد، به هر عنصر هیستوگرام RPD هم اضافه شد، و طبقه‌بندی کیفیت از «درصد بالای آستانه‌ها» به «میانگین + انحراف معیار RPD» تغییر کرد (مطابق رویکرد Thompson-Howarth). در حالت `auto` زوج‌ها از ردیف‌های هم‌جوار فرد/زوج ساخته می‌شوند (آزمایشی — برای داده‌ای که زوج‌ها پشت سر هم درج شده‌اند).
- **باگ حین کار:** فراخوانی `datetime.now()` بدون import (نمایش تاریخ در شیت تنظیمات) → `from datetime import datetime` به هدر `processing_services.py` اضافه شد. هرداک bash در ویندوز دو بار به‌صورت ناقص بسته شد و انتهای فایل را خراب کرد — هر دو بار با rollback از انتهای سالم (خط ۲۳۱۵) و الحاق مجدد از طریق فایل موقت حل شد.

### ب) روش‌های درون‌یابی و رسم نقشه — امکان انتخاب بین چند روش (هدف اصلی)
- **وضعیت فعلی:** فقط IDW پیاده‌سازی شده و به‌صورت **موقت** انتخاب شده است، صرفاً برای دور ماندن از چالش تنظیم پارامترهای کریجینگ. هدف نهایی، امکان **انتخاب بین چند روش درون‌یابی** توسط کاربر است.
- **روش هدف/بهینه برای داده‌های ژئوشیمی: کریجینگ جهت‌دار (Anisotropic / Directional Kriging).** برخلاف IDW که فقط بر اساس فاصله وزن می‌دهد، کریجینگ جهت‌دار ساختار مکانی واقعی کانی‌سازی (که معمولاً همسانگرد نیست و در امتداد روند زمین‌شناسی/ساختاری کشیدگی دارد) را از طریق واریوگرام مدل می‌کند و نتیجه دقیق‌تری برای داده‌های اکتشافی می‌دهد.

**چالش اصلی کریجینگ جهت‌دار:** برازش پارامترهای واریوگرام (nugget، sill، range، و برای حالت جهت‌دار: زاویه آنیزوتروپی و نسبت آنیزوتروپی) دستی و نیازمند تخصص ژئواستاتیستیک است؛ برازش خودکار نادرست می‌تواند نتیجه گمراه‌کننده بدهد.

**پیشنهاد پیاده‌سازی مرحله‌ای:**
1. **کوتاه‌مدت (بهینه‌سازی همین IDW موقت):** جایگزینی حلقه دوتایی فعلی در `_idw_interpolation` با `scipy.spatial.cKDTree` (به‌جای broadcasting ساده NumPy، چون برای گریدهای بزرگ حافظه ماتریس فاصله کامل مشکل‌ساز می‌شود). این کار فقط سرعت را بهبود می‌دهد و در انتظار افزودن کریجینگ، موقتاً کارآمدتر می‌ماند:

```python
from scipy.spatial import cKDTree
import numpy as np

def idw_interpolation_kdtree(grid_x, grid_y, points_x, points_y, values, power=2, k=12):
    tree = cKDTree(np.column_stack([points_x, points_y]))
    grid_points = np.column_stack([grid_x.ravel(), grid_y.ravel()])

    dist, idx = tree.query(grid_points, k=k)
    dist = np.where(dist == 0, 1e-10, dist)   # جلوگیری از تقسیم بر صفر

    weights = 1.0 / dist**power
    z = (weights * values[idx]).sum(axis=1) / weights.sum(axis=1)

    return z.reshape(grid_x.shape)
```
   پارامتر `k` (تعداد همسایه‌ها) بین ۸ تا ۱۵ باشد، ترجیحاً قابل‌تنظیم توسط کاربر. جایگزینی داخل `processing_services.py` انجام شود و خروجی قبل/بعد روی یک نمونه تست مقایسه شود.

2. **میان‌مدت (هدف اصلی — افزودن کریجینگ به‌عنوان روش انتخابی):**
   - از کتابخانه `pykrige` (کلاس `OrdinaryKriging` با پارامترهای `anisotropy_angle` و `anisotropy_scaling`) یا `gstools` (که ابزار برازش خودکار واریوگرام — `gstools.covmodel.fit_variogram` — دارد) استفاده شود.
   - برای مقابله با چالش برازش پارامترها:
     - در گام اول، **برازش خودکار** واریوگرام تجربی (مدل‌های spherical/exponential/gaussian) با یکی از دو کتابخانه بالا انجام شود و پارامترهای پیشنهادی (nugget, sill, range, انگل و نسبت آنیزوتروپی) به کاربر نمایش داده شود.
     - در کنار آن، امکان **override دستی** پارامترها برای کاربر متخصص (مثل شما) فراهم شود، به‌همراه نمایش واریوگرام تجربی در برابر مدل برازش‌شده (نمودار) تا کیفیت برازش قابل ارزیابی بصری باشد.
   - معماری کد: هر روش درون‌یابی (IDW، Ordinary Kriging، Directional Kriging) به‌صورت تابع مستقل پیاده‌سازی شود و از طریق یک پارامتر انتخاب روش (مثلاً `interpolation_method`) در روت مربوطه انتخاب‌پذیر باشد — تا افزودن روش‌های بعدی (مثل RBF) هم ساده بماند.
   - وابستگی جدید (`pykrige` یا `gstools`) باید به `requirements.txt` اضافه شود.

3. **انتخاب عنصر/ستون برای نقشه‌سازی (پیش‌نیاز UI):** فعلاً باید مشخص شود کاربر برای کدام عنصر(ها) نقشه بخواهد بسازد — نه لزوماً همه ستون‌ها، چون تعداد عناصر/کانال‌ها می‌تواند زیاد باشد و تهیه نقشه برای همه آن‌ها هم زمان‌بر است و هم لزوماً موردنیاز نیست.
   - **رفتار موردنیاز:** انتخاب **یک عنصر**، **چند عنصر مشخص**، یا **همه عناصر** — هر سه حالت باید پشتیبانی شوند (نه فقط تک‌انتخابی یا همه).
   - **ساماندهی UI برای تعداد زیاد ستون‌ها** (چون یک چک‌باکس ساده برای ده‌ها عنصر قابل‌استفاده نیست):
     - یک باکس چندانتخابی (multi-select) با **قابلیت جست‌وجو/فیلتر با تایپ نام عنصر** (مثلاً با یک کتابخانه سبک جاوااسکریپتی مثل Choices.js یا Select2، بدون نیاز به فریم‌ورک سنگین).
     - دکمه‌های میان‌بر «انتخاب همه» و «حذف انتخاب».
     - در صورت امکان، گروه‌بندی عناصر (مثلاً فلزات پایه، فلزات گرانبها، عناصر نادر خاکی — بر اساس ستون‌های ورودی فایل) برای انتخاب سریع یک گروه.
     - نمایش تعداد عناصر انتخاب‌شده (مثلاً «۵ از ۲۴ عنصر انتخاب شده») تا کاربر قبل از اجرای پردازش سنگین، انتخاب خود را تأیید کند.
   - **در بک‌اند:** روت رسم نقشه باید لیست نام ستون‌های انتخابی را از کلاینت بگیرد و فقط برای همان‌ها درون‌یابی/رسم انجام دهد (نه پیمایش خودکار همه ستون‌های عددی فایل).

### ج) افزودن تست خودکار
- پروژه فاقد هرگونه تست است. پیشنهاد می‌شود با `pytest` تست‌های واحد برای توابع هسته‌ای بنویسید:
  - `outliers.py` (روش‌های IQR، Z-Score، Dorfel)
  - منطق پردازش سانسور در `processing_services.py`
  - توابع تبدیل نرمال (Box-Cox، Yeo-Johnson، Quantile، Log، Sqrt، Rank-Based)

### د) بهبود مدیریت پیکربندی
- انتقال مقادیر ثابت پراکنده در کد (پورت، حداکثر حجم فایل، ضرایب سانسور پیش‌فرض، مسیر پوشه‌های upload/output/session) به یک فایل `config.py` یا متغیرهای محیطی (`.env`) واحد، به‌جای پخش‌شدن در چند فایل.

### ه) مستندسازی API داخلی
- روت‌های زیادی (۲۴ روت در `geochemistry_analysis_app.py`) بدون مستندسازی رسمی هستند. پیشنهاد می‌شود یک فایل `API.md` یا Swagger/OpenAPI ساده برای اندپوینت‌های اصلی (`/upload`، `/get_columns`، `/save_coordinates`، `/process_censored`، `/download/...` و غیره) تهیه شود تا نگهداری و توسعه بعدی راحت‌تر باشد.

### و) ادغام ماژول «داده‌های تکراری» (`app.py`) در اپ اصلی به‌عنوان یک تب
- **وضعیت فعلی:** `app.py` یک اپ Flask جدا و مستقل است که فایل را آپلود می‌کند، با `subprocess.run(['python', 'read_duplicate_parallel.py', ...])` اسکریپت خارجی را اجرا می‌کند، و نتایج (کیفیت تکرار بر اساس RPD، نمودارهای پراکندگی/Thompson-Howarth) را برمی‌گرداند.
- **مشکل ۱ — جدا بودن از پایپ‌لاین اصلی:** کاربر باید بین دو اپ جابه‌جا شود. باید تحلیل داده‌های تکراری به‌صورت یک **تب جدید** در `geochemistry_analysis_app.py` (در کنار تب‌های سنسورد، Outliers، آمار توصیفی و ...) درآید، نه اپ جدا. منطق `read_duplicate_parallel.py` می‌تواند به‌جای فراخوانی با `subprocess`، مستقیماً به‌عنوان تابع import و در `processing_services.py` یکپارچه شود (سریع‌تر و بدون سربار پردازش جدا).
- **مشکل ۲ — حساسیت شدید به نام شیت و نام ستون:** `read_duplicate_parallel.py` نام شیت‌ها (`'Duplicate Samples'`, `'Duplicate_Data'`) و نام ستون‌ها (`'Sample_ID'`, `'Duplicated_Sample_ID'`) را دقیقاً و هاردکد انتظار دارد (خطوط ۲۷-۲۸ و ۱۸۷). اگر فایل ورودی این نام‌ها را عیناً نداشته باشد، پردازش با خطا متوقف می‌شود.
  - **راه‌حل:** مشابه الگوی موجود در تب‌های دیگر اپ اصلی (که قبلاً برای انتخاب ستون مختصات X/Y به کاربر منوی کشویی می‌دهند — روت‌های `/get_columns` و `/save_coordinates`)، یک مرحله «تطبیق ستون‌ها» اضافه شود: بعد از آپلود، لیست شیت‌ها و ستون‌های فایل به کاربر نمایش داده شود تا شیت نمونه‌های تکراری، ستون شناسه نمونه اصلی و ستون شناسه نمونه تکراری را خودش انتخاب کند (به‌جای اتکا به نام‌های ثابت).
- **مشکل ۳ — عدم دسترسی به تصحیح داده‌های سانسورشده قبل از اجرا:** در حال حاضر داده‌های تکراری مستقیماً و بدون امکان تصحیح مقادیر سانسورشده (`<`/`>`) پردازش می‌شوند؛ درصورتی‌که داده خام معمولاً به این تصحیح نیاز دارد و نتیجه تحلیل تکرار (RPD) بدون آن می‌تواند نادرست باشد.
  - **راه‌حل:** با ادغام این ماژول در پایپ‌لاین اصلی (مشکل ۱)، کاربر بتواند ابتدا از تب «پردازش داده‌های سنسورد» موجود در همان اپ برای تصحیح داده استفاده کند و سپس خروجیِ تصحیح‌شده را به‌عنوان ورودی تحلیل داده‌های تکراری بدهد — یعنی این تب باید بعد از تب سنسورد در ترتیب pipeline قرار گیرد و بتواند از session جاری (داده تصحیح‌شده) استفاده کند، نه فقط از یک فایل تازه آپلودشده مجزا.
